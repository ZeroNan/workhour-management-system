## 1. 产品目标

本增量（v2）目标：将工时管理系统从"单机演示版"升级为"可真实部署、多用户可靠使用"的最小可用产品。

1. **堵住两条核心数据质量漏洞**：禁止 PM 自审自己的工时、禁止填报未来日期，保证工时数据作为管理/结算依据的可信度。
2. **数据后端持久化**：核心数据（组织架构、项目、人员、工时记录、审核流转）入库存储，前后端完整交互，摆脱 localStorage 演示属性。
3. **真实部署上线**：系统在实际运行环境（服务器/内网/云主机）可被多用户并发访问，核心流程（填报、审核、校验、统计、导出）稳定可用。

**价值**：工时数据从"演示样本"变为"生产数据"，可作为绩效考核、项目成本核算的输入；审核流程合规（自己不能审自己），消除数据造假与倒填隐患。

**非目标（本版不做）**：工时锁定月度关账、多级审批、跨项目工时冲突检测、消息通知（邮件/IM）、移动端适配、权限细粒度自定义。

## 2. 用户故事

### 2.1 管理员

- US-A1：作为管理员，我希望所有数据保存在服务器数据库中，这样多人同时使用时数据不丢失、不互相覆盖，浏览器关闭或换电脑后数据仍在。
- US-A2：作为管理员，我希望用账号密码登录系统，密码不以明文存储，这样系统能安全地暴露给团队真实使用。
- US-A3：作为管理员，我希望系统预置一套演示数据（部门/项目/人员/工时样本），这样上线后无需从零手工录入即可演示和验证功能。
- US-A4：作为管理员，我希望按项目/按成员的统计与 Excel 导出仍然可用，且导出内容与后端数据一致，便于我向管理层汇报。

### 2.2 项目负责人（PM）

- US-P1：作为 PM，当我自己也是项目成员并提交了工时，我希望系统不允许我审核自己的记录，并提示由谁来审（如上级管理员），这样审核结果才可信。
- US-P2：作为 PM，我希望批量审核时自动跳过"我自己提交"的记录并明确提示跳过了几条，避免批量操作后才发现有漏审。
- US-P3：作为 PM，我希望其他成员与我同时操作（如我审核时成员撤回/修改）时，系统给出明确结果（成功/失败原因），而不是静默覆盖或报错崩页。

### 2.3 研发人员

- US-D1：作为研发人员，我希望填报/补录/修改时，选择晚于今天的日期会被直接拦截并提示，这样我不会误填未来日期导致记录无效。
- US-D2：作为研发人员，我希望我在个人月度视图里看不到未来日期列（或置灰不可填），界面即约束，不用提交后才报错。
- US-D3：作为研发人员，我希望登录一段时间不操作后自动退出需重新登录，防止别人用我的会话乱填；重新登录后我能接着刚才的工作继续。
- US-D4：作为研发人员，我希望已保存但未提交的工时存在服务器上，换电脑登录后能继续编辑，不依赖某一台浏览器。

## 3. 需求池

优先级定义：P0 = 本版必须交付；P1 = 建议本版交付（低成本高价值）；P2 = 后续版本。

### 3.1 P0（本版必须）

| 编号 | 需求 | 描述 | 验收标准 |
|---|---|---|---|
| P0-1 | 禁止 PM 自审 | PM 对自己提交的工时记录无审核权限（前端不展示审核按钮 + 后端强校验双保险） | ① PM 打开自己工时记录时无"通过/退回"入口；② 直接调 API 审核自己记录返回 403 及明确错误信息；③ 批量审核时自动跳过本人记录，响应中逐条标明 skip 及原因 |
| P0-2 | 自审禁止后的兜底审核 | PM 本人记录的审核路径：默认由管理员代审（本版不引入新角色） | ① PM 记录提交后进入"待审核"且审核人指向管理员（或管理员审核视图可见）；② 管理员可对该记录执行通过/退回；③ 产品文档/界面提示"PM 本人记录由管理员审核" |
| P0-3 | 禁止未来日期（写入侧） | 填报、补录、修改时的"工时日期"不得晚于当天（服务器日期为准） | ① 前端日期选择器 max = 今天；② 后端对 date > 今天（按服务器时区）一律拒绝，返回明确错误；③ 修改历史记录改日期同样受此约束；④ 跨天边界场景（23:59 填报、00:01 提交）以后端收到请求时的服务器日期为准 |
| P0-4 | 未来日期（展示侧） | 月度视图/统计视图不再渲染未来日期列 | ① 个人月度视图与管理员统计视图的日历列仅渲染到"今天"；② 已存在的非法未来记录（历史脏数据）在视图中置灰标注"异常"，不参与合计；③ 列头"今天"高亮 |
| P0-5 | 后端服务与数据库持久化 | 提供后端 API（建议 Node.js/Express 或同类轻量栈 + SQLite/MySQL），承载人员/部门/项目/工时/审核全量数据 | ① 所有业务数据仅存于数据库，重启服务后数据完整；② v1 的核心接口（登录、CRUD、提交、审核、统计）全部走 HTTP；③ 前端不再读写 localStorage 业务数据 |
| P0-6 | 登录与会话 | 账号密码登录，服务端会话（Session + Cookie 或 JWT），支持登出 | ① 未登录访问任何业务接口返回 401 并引导到登录页；② 密码使用 bcrypt 等加盐哈希存储，库中无明文；③ 登出后会话立即失效 |
| P0-7 | 会话过期处理 | 会话超时自动失效 | ① 超时（默认 8 小时，待确认）后业务请求返回 401，前端统一拦截弹提示"登录已过期"并跳登录页，登录后回到原页面；② 过期前用户正在编辑但未保存的内容不静默丢失（至少保留在表单中待用户手动处理） |
| P0-8 | 并发冲突与幂等 | 多用户同时编辑/审核的一致性表现 | ① 审核接口幂等：对同一记录重复提交相同审核结果返回成功且不产生重复记录；② 提交/审核基于记录版本或状态机（如仅"未提交/已退回"可编辑，仅"待审核"可审核），状态不匹配返回 409 及原因（如"该记录已被审核/已被修改，请刷新"）；③ 前端收到 409 时提示并自动刷新数据 |
| P0-9 | 部署上线 | 在实际环境部署运行 | ① 提供部署说明文档（环境依赖、启动命令、数据库初始化、数据备份方式）；② 服务以生产模式启动（如 pm2/systemd），崩溃可自动拉起；③ 部署后冒烟清单全通过：登录→填报→提交→审核→统计→导出 |
| P0-10 | 演示数据迁移策略 | 后端重新种一套演示数据，废弃前端 localStorage 旧数据 | ① 首次初始化自动写入演示部门/项目/人员/样本工时；② 前端登录后只展示后端数据；③ localStorage 中的 v1 旧业务数据不再读取（可静默忽略，不迁移）；④ 演示数据标识清晰，管理员可一键清空演示数据转为正式使用（P1 增强此项体验） |
| P0-11 | Excel 导出 | 导出与后端数据一致的统计报表 | ① 按项目统计、按成员×日期矩阵两种导出保持 v1 口径；② 导出内容与页面统计一致（同源于后端查询）；③ 文件命名含统计范围（如 `工时统计_2026-09.xlsx`） |

## 4. 两条规则的精确产品定义

### 4.1 自审禁止的边界

**规则**：当 `审核人 == 记录提交者本人` 时，禁止执行通过/退回操作（前端隐藏入口 + 后端 403）。

**边界判定（默认采用方案 A）**：

| 方案 | 定义 | 建议 |
|---|---|---|
| A（默认） | 仅禁止"审核人 = 提交者本人"。同项目两名 PM 互相审核对方的工时**允许** | ✅ 推荐：实现简单、语义清晰；互相审核在中小团队是常见实践，数据可信度损失有限 |
| B | 同项目成员之间互相审核全部禁止，一律上收管理员 | ❌ 暂不采用：会给管理员带来大量代审负担，需等委托审核（P2-3）配套后再考虑 |

**补充细则**：
- 判定以"记录的提交者"为准，而非"项目 owner"字段——即只要这条工时是 PM 本人提交的，本人就不能审，无论他是否为该项目 owner。
- PM 修改自己的工时后重新提交，仍适用本规则。
- 批量审核请求中混入本人记录：跳过该条并在结果中逐条反馈，其余正常处理（整体不因部分失败而回滚）。

### 4.2 未来日期的精确边界

**规则**：`工时日期 > 今天` 即拦截（以**服务器日期**为准，含当天 → **当天允许填报**）。

| 场景 | 行为 |
|---|---|
| 新增填报 | 日期选择器 max=今天；后端二次校验，date > 今天返回 400 |
| 补录历史 | 同上（任意过去日期允许，另受 P2-1 关账约束预留） |
| 修改历史记录 | 若修改涉及日期字段，新日期同样不得 > 今天；不修改日期则不受影响 |
| 跨天提交 | 提交时刻以服务器时间为准：23:59 填了"今天"、00:01 才保存→该日期已变"昨天"，仍合法（过去日期） |
| 个人月度视图 | 当月未来日期列**不渲染**（日历列仅到今天），"今天"列头高亮 |
| 管理员统计视图 | 同上，列仅到今天；历史脏数据中的未来记录置灰标"异常"、不参与合计、不计入导出 |

**为何选"不渲染"而非"置灰"**：不渲染可彻底杜绝用户误操作，且实现上无需为未来列做禁用逻辑；置灰仅在展示历史脏数据时使用（保留追溯能力）。

## 5. Excel 导出：前端 or 后端？（建议）

**建议：P1 阶段改为后端生成**，理由：

1. **数据一致性**：后端生成可复用与统计页相同的查询逻辑，杜绝"页面显示 A、导出 B"的口径漂移。
2. **数据量与性能**：全年全员矩阵（30 人 × 365 天）在浏览器端生成易卡顿；后端生成+流式下载更稳。
3. **权限收口**：导出是全量敏感数据出口，后端可统一鉴权、记录谁在何时导出了什么（为 P2-5 审计打基础）。
4. **迭代成本**：v1 已有导出逻辑，本版可先保留前端导出（P0-11）保证功能不回退，后端导出作为 P1 平滑替换。

## 7. 验收方式（概要）

1. 功能验收：按 P0 验收标准逐条过（自审 403、未来日期 400、跨天边界、并发 409）。
2. 数据验收：重启后端服务，数据无损；浏览器换机登录，数据一致。
3. 并发验收：双浏览器双用户同时操作同一记录，观察幂等与冲突提示。
4. 部署验收：按部署文档在目标环境从零拉起，冒烟清单全通过。
